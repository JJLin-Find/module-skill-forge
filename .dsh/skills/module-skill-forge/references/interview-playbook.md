# 访谈手册：把代码事实问成模块知识

访谈的目的不是收集需求，而是**补齐代码里没有、但做需求/修 bug/答疑时必须知道的东西**。凡是 `grep`/`read` 能得到的，都不要问。

## 1. 访谈节奏

| 轮次 | 时机 | 问数 | 主题 |
|---|---|---|---|
| 定界轮 | P1 扫描后、P2 补读前 | 1–3 | 模块边界、本次任务场景、深浅 |
| 语义轮 | P2 补读后 | 3–4 | 代码读不出的语义：不变量、边界、业务规则 |
| 故障轮 | 生成前 | 2–4 | 线上故障表现、踩坑、评审/发布约定 |

两轮足够；用户愿意多说就多听，不要为了凑题硬问。`quick` 模式只问 3 个：模块边界、最常改哪里、最怕改坏什么。

## 2. 问句公式

```
【推断】我从 <证据路径> 看到 <具体发现>，我理解 <业务含义>。
【请确认】这个理解对吗？还有哪些情况我没覆盖？
```

要求：

- 每条推断必须挂一条真实证据（路径，最好带行号或符号名）。
- 一次只问一个决策点；多个小问题合并成一道多选题。
- 给选项，选项要具体（「A. 订单创建时锁库存 / B. 支付成功时锁库存」），不要「是/否」空问。
- 把「我不知道」当成合法答案，并当场转 `TODO(待确认)` 落到文件里。

## 3. 六类题库

### 3.1 边界与职责（问 1–2 个）

- 这个模块**不负责**什么？哪些看起来相关但其实由别的模块/服务处理？（防越界改动）
- 对外承诺的接口稳定吗？哪些字段/行为是契约，哪些是实现细节？
- 有没有「临时方案/历史包袱」，现在还不能动？
- 入口从哪来：HTTP 路由、定时任务、消息、CLI、被其他包 import？哪个是主路径？

带证据的问法：「`packages/catalog/src/index.ts` 导出了 5 个符号，但 `README` 只提到 2 个，其余 3 个是给谁用的？」

### 3.2 不变量与数据（问 1–2 个）

- 哪些字段/状态一旦写错就出事？谁负责保证（数据库约束、代码校验、上游）？
- 状态流转图（草稿→已支付→已发货…）里有没有非法跃迁？现在靠什么拦住？
- 数据保留/删除策略？有没有软删除、归档、多租户隔离？
- 金额/时间/ID 这些敏感值用什么表示（分 vs 元、UTC vs 本地、字符串 vs 数字）？

带证据的问法：「`pricing.ts` 里价格用整数分存储，但 `cart.ts` 有一次 `/100`，这是展示层约定还是 bug？」

### 3.3 故障与排障（问 1–2 个）

- 这个模块线上出过什么问题？日志里长什么样？你先看哪个指标？
- 「看起来正常但结果不对」最可能的原因是什么？
- 本地能复现吗？需要什么数据/环境/开关？
- 有没有已知的 flaky 测试、偶发超时、依赖不稳定的下游？

带证据的问法：「`order-service.ts:84` 调用 catalog 没有超时设置，线上会不会拖垮结算？现在的兜底是什么？」

### 3.4 术语与语义（问 0–1 个）

- 这几个词在你们业务里分别指什么：A / B / C？（代码里混用的）
- 同一个概念在不同层是否换了名字（DTO/实体/前端模型）？
- 有哪些「看起来一样其实不同」的东西（两个 status、两种 id）？

### 3.5 流程与协作（问 1–2 个）

- 改这个模块要通知谁？有没有必须同步的文档/下游/配置？
- 发布流程：灰度、开关、回滚方式？数据库迁移怎么走？
- 评审时最常被指出的问题是什么？
- 分支/提交/版本约定（如果 AGENTS.md / CONTRIBUTING 里没写清）。

### 3.6 验证（问 1 个）

- 验证改动的最小充分命令是什么（单测过滤、本地起服务、造数）？
- 有没有必须手动验证的场景（付费、发货、权限）？
- 测试里哪些是「假绿」（mock 掉了关键路径）？

### 3.7 需求与口径（knowledge 取向必问，2–3 个）

- 这条需求当时要解决什么问题？验收标准是什么（谁签字/什么现象算完成）？
- 有没有「实现和最初需求不一致」的地方，现在的实际规则以哪个为准？
- 金额/时间/ID/状态这些口径：单位、时区、默认值、边界值分别是什么？
- 哪些行为是业务硬约束（改了要出事），哪些只是当前实现方式（可以优化）？

带证据的问法：「`pricing.ts:52` 把折扣封顶 20%，这是业务定的还是当时随手写的？超了会怎样？」

### 3.8 新人困惑（knowledge 取向必问，2–3 个）

- 新人第一次看这个模块，最容易误解什么？最容易改错哪里？
- 有哪些「名字像但其实是两个东西」的概念？
- 哪些问题被反复问到？（这些直接进 `faq.md`）
- 熟手 30 分钟会怎么带新人过一遍？

带证据的问法：「`cart.ts` 和 `order-service.ts` 都算总价，新人该以哪个为准？」

## 4. 反例 → 正例

| 反例（不要问） | 为什么坏 | 正例 |
|---|---|---|
| 「这个模块是做什么的？」 | 代码/README 里有 | 「`cart.ts` 和 `order-service.ts` 都计算总价，哪个是权威？我猜 checkout 层是最终口径，对吗？」 |
| 「你想让我怎么写这个技能？」 | 把工程决策推给用户 | 「我打算按『改价格逻辑 / 加折扣规则 / 排查金额对不上』三条场景组织，缺一条吗？」 |
| 「有没有什么坑要注意？」 | 太泛，答案不可用 | 「变更 `pricing.ts` 的折扣顺序时，`product-store.test.ts` 之外的哪些用例可能挂？」 |
| 「要写测试吗？」 | 不是知识 | 跳过，直接给验证命令让用户确认 |

## 5. 答案如何落盘

| 用户回答 | 落到哪里 |
|---|---|
| 职责边界、调用链、状态机 | `references/architecture.md` |
| 「改 X 去 Y 文件」 | `references/file-map.md` |
| 修改步骤、跑什么命令 | `references/workflows.md` 与 `verification.md` |
| 故障现象→原因→处理 | `references/pitfalls.md` |
| 术语、命名差异 | `references/../conventions.md`（总览）或 `architecture.md` 术语表 |
| 流程、通知对象、发布/回滚 | `references/../conventions.md`（总览） |

回答里的代码事实同样要标路径；用户口述但无法在代码中核实的，写成「据维护者：……」并标 `TODO(待确认)`。

## 6. 边界情况处理

- **用户只说一句「你看着办」**：按扫描结果出 `full` 版本，所有推断标 `TODO(待确认)`，报告里给出 3 条最该确认的问题。
- **用户一次回答很多**：复述成 3 条要点请其确认，避免把闲聊写进技能。
- **回答与代码冲突**：以代码为准描述现状，把冲突单独写成「⚠️ 文档/口述与代码不一致」条目，请用户裁决。
- **问了两轮仍有关键空白**：不要编，列进 `TODO(待确认)` 并在交付报告中置顶。
