# 交付件规格：生成什么、每节写什么、什么算不合格

生成物只有两类技能包。任何一份都必须能**独立回答**「什么时候该加载我」和「加载后第一步做什么」。

## 1. 命名与位置

| 项 | 规则 | 例 |
|---|---|---|
| 技能目录 | kebab-case，必须带项目前缀防全局重名 | `sample-shop-overview`、`sample-shop-catalog-dev` |
| 模块技能名 | `<项目>-<模块>-dev`；模块本身已含项目名的可简写 | `acme-api-billing-dev` |
| 总览技能名 | `<项目>-overview` | `sample-shop-overview` |
| 位置 | `<项目根>/.dsh/skills/<技能名>/` | 与 `module-skill-forge` 同级 |
| frontmatter | 只写 `name` + `description`；需要时加 `whenToUse` | 不要写 path/version/author 等未定义键 |

`description` 公式：

```
当<用户任务/症状>时使用：<它能带来什么判断或动作>。<可选的边界说明>
```

- 写「任务」不写「模块介绍」：好 `当需要给目录模块加折扣规则时使用：给出改动点、影响面与回归命令`；坏 `本技能介绍商品目录模块，包含商品与价格两部分`。
- 40–300 字符；≤500 是硬上限（超了目录会截断）。
- 中文用「当…时使用」，英文用 `Use when …`；其余语言同理。
- 不要写「本技能…」开头——路由时模型只看到这一行。

## 2. 模块技能 `SKILL.md`（≤120 行）

固定骨架（模板见 `assets/templates/module.SKILL.md.tmpl`）：

0. **基线标记**：frontmatter 之后第一行写 `<!-- forge: module=<模块路径> facts=<事实包路径> scanned=<日期> head=<git HEAD 或 none> -->`。它让 `refresh.py` 在不读正文的情况下判断技能是否过期；换模块/重扫后必须同步更新。总览技能写 `module=* facts=none`（表示全局技能，不随单模块判定过期）。
1. **标题 + 三行定位**：模块一句话职责、它不负责什么、最重要的一个风险。
2. **先做什么（3 条主流程）**：需求开发 / 修 bug / 答疑，每条 3–5 步，每步带「读哪个文件、跑什么命令」。
3. **读取指引**：5 个 references 各一句「何时读」。
4. **关键事实速查**（可选，≤10 条）：入口、状态存储、命令、环境变量、依赖方向。
5. **边界**：本技能不管什么（交回给哪个技能/需要人确认）。

写法要求：

- 动词开头，命令可复制；不要解释背景故事。
- 每条结论带相对路径；路径写在行内反引号里。
- 主流程必须能照做：第 1 步永远是「读 X」，第 2 步是「改 Y」，最后是「跑 Z 验证」。
- 不贴大段代码（>15 行）；引用文件与符号名即可。

## 3. 模块技能 `references/*.md`（各 ≤200 行）

| 文件 | 必须回答的问题 | 不合格信号 |
|---|---|---|
| `architecture.md` | 职责边界、入口清单、调用链（文字版时序）、数据流、状态机、不变量、外部依赖 | 只有目录树，没有“谁调用谁” |
| `file-map.md` | 「我要改 X 去哪个文件/符号/测试」的映射表（按意图分组，不按目录分组） | 复述目录结构，没写「改什么去哪」 |
| `workflows.md` | 三条流程的完整步骤：前置检查 → 改动点 → 验证 → 提交前自检 | 步骤缺验证命令 |
| `pitfalls.md` | 故障现象 → 可能原因 → 排查命令 → 修复方向；已知缺陷/TODO | 只写「注意空指针」这类废话 |
| `verification.md` | 真实命令（含前置条件、过滤单测、环境变量）、预期输出、手动验证场景 | 出现事实包里没有的命令 |

规则：

- 每个 reference 顶部写一句「读这个文件是为了解决什么问题」，方便模型判断是否继续读。
- 交叉引用写相对路径（如 `references/file-map.md`），不要引用项目之外的绝对路径。
- 表格优先于长段落；一屏能扫完。
- 事实与推断分开：推断放「推测」小节或标 `TODO(待确认)`。

### 3.1 knowledge 取向追加的两份（模块已实现稳定、有新人答疑需求时）

| 文件 | 必须回答的问题 | 不合格信号 |
|---|---|---|
| `business-spec.md` | 已实现需求清单、业务规则、字段口径、状态流转、历史决策与不能动的部分、业务术语 | 只复述代码行为，没有「业务上为什么」 |
| `faq.md` | 新手 30 分钟路线；入门 / 业务规则 / 改代码 / 排障四组问答；维护约定 | 问题像是编的；答案没有代码位置 |

写法：

- `business-spec.md` 每条规则都要有「来源」（代码路径，或「据维护者」+ `TODO(待确认)`）；验收标准写成可观察的现象，不写「功能正常」。
- `faq.md` 的问题用**新人原话**；每条按「简答 → 细节（带路径）→ 相关需求」写，≥8 条起步。
- 两份只写「稳定的知识」：需求还在频繁变动的模块先做 `dev` 取向，等稳定了再补。
- 生成后每次被问到新问题，就回写一条到 `faq.md`（见 validation-and-maintenance 的「知识沉淀」）。

## 4. 总览技能 `<项目>-overview`

`SKILL.md`（≤120 行）：

- 项目一句话定位 + 技术栈 + 目录布局（只列顶层）。
- **模块路由表**：任务 → 该加载哪个技能（这是总览最重要的产出）。
- 全局命令（安装/构建/测试/lint/起服务、前置条件）。
- 跨模块约定入口 + 何时该回到总览。

`references/module-map.md`：模块表（路径、职责、维护者、上下游、健康度/风险）+ 模块间依赖图（文字）+ 常见跨模块任务的路由。

`references/conventions.md`：分支/提交/评审、发布与回滚、环境变量与配置、代码风格与测试要求、术语表、决策记录链接。

总览技能**不写实现细节**；一旦开始写某模块函数，说明该内容应该落到模块技能里。

## 5. 反例清单（生成后逐条自查）

1. 技能读起来像「项目介绍/架构散文」→ 删，改成任务路由。
2. 出现 `TODO` 以外的空话：「注意兼容性」「保持代码整洁」→ 换成具体检查项或删。
3. 命令是猜的/旧版本 → 回到事实包核对，或标 `TODO(待确认)`。
4. 同一份内容在 SKILL.md 和 references 里重复 → 只保留一份，另一处放指针。
5. `description` 超过 300 字符或写成功能列表 → 重写。
6. 引用绝对路径、内网地址、密钥/账号 → 删除，改为配置项名称。
7. references 之间循环引用（A 说看 B，B 说看 A）→ 指定一个权威文件。
8. 写了「本模块没有任何问题」这类结论 → 无证据不写。

## 6. 质量标尺（交付前自评）

- 新人拿到模块技能，能在 10 分钟内完成一次「找到改动点 + 跑通验证」。
- 老手看 `pitfalls.md` 能认出「这确实是我们踩过的坑」。
- 每一节都能追溯到代码路径或用户回答；`TODO(待确认)` 数量 ≤5 且有清单。
- 任意两个技能不重复讲同一件事：模块细节在模块技能，全局规则在总览。

## 7. 参考样例（黄金输出）

交付仓 `examples/sample-shop-skills/` 是一份完整的黄金输出（由合成仓库 `fixtures/sample-shop` 生成），结构与本规格一致：总览技能 3 个文件、模块技能 6 个文件。若技能包被单独复制到别的项目，按以下要点还原同一形态：

- `SKILL.md` 前 10 行内必须出现：职责一句话、不负责什么、最大风险（带路径）。
- 三条主流程每条 4–5 步，首步是「读哪个文件」，末步是「跑什么命令 + 预期」。
- `file-map.md` 按「我要改…」组织表，而不是按目录列文件。
- `verification.md` 的每条命令都标来源（`package.json` script 名）与前置条件。
- 出现不确定处写 `TODO(待确认)：<缺什么>`，并在交付报告里汇总。

## 8. 自查清单（复制到回复里逐条打勾）

- [ ] 两份技能的 `description` 都能让不相干的模型判断「不该加载我」
- [ ] 每个代码事实都有相对路径，命令都有来源
- [ ] 三条主流程能照着做完，不需要额外提问
- [ ] references 无重复内容、无相互循环引用
- [ ] knowledge 取向：`business-spec.md` 每条规则有来源，`faq.md` 每条答案有代码位置、问题像新人原话
- [ ] `TODO(待确认)` 已汇总且 ≤5 条
- [ ] 校验器 0 error，warning 已逐条处理
