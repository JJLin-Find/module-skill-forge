# 证据规则：什么可以写进技能，怎么写

技能会被模型当成事实使用。**一条没有依据的结论，比缺一条更危险。**

## 1. 证据等级

| 等级 | 来源 | 写法 | 可用性 |
|---|---|---|---|
| A 代码 | 源码、配置、测试、脚本 | `packages/catalog/src/pricing.ts:42` | 直接陈述 |
| B 命令 | `package.json` scripts、Makefile、CI 配置 | 「命令来源：`package.json` → `scripts.test`」 | 可直接执行 |
| C 用户口述 | 访谈回答 | 「据维护者：…（未在代码中核实）」 | 陈述 + 标 `TODO(待确认)` |
| D 推断 | 你自己从命名/结构推理 | `TODO(待确认)：推测 …，依据 <路径>` | 不得写成事实 |

规则：A/B 是主体；C 要标记来源；D 默认不进技能，除非明确标注且数量受控。

## 2. 路径写法

- 一律相对**项目根**，正斜杠，不带 `./`：`packages/catalog/src/index.ts`。
- 行号用于指认具体位置：`src/pricing.ts:42`；行号会漂移，所以同时给符号名。
- 禁止宿主绝对路径（用户主目录、系统盘符形式的完整路径）、禁止 `file://`。
- 引用其他技能用技能名：`sample-shop-overview`。

## 3. 命令的核实方式

1. 只从事实包 `commands[]` 里取；每条命令都能在 `package.json`/`Makefile`/`pyproject.toml` 里指到出处。
2. 需要组合时（如跑单个测试），基于真实命令派生：`pnpm --filter @sample/catalog test -- product-store`。派生要在 `verification.md` 标注「派生自 …」。
3. 事实包没有、用户也说不清的 → `TODO(待确认)：验证命令`，不要编。
4. 命令必须包含前置条件（安装、环境变量、需要起的服务），否则写了也跑不通。

## 4. 事实与推断的边界

- 代码能证明「做了什么」；代码证明不了「为什么这么做」和「业务上对不对」——后者只能来自用户。
- 同一个行为在多处实现矛盾时：以**被调用方/最接近数据**的实现为现状口径，把矛盾单列为「⚠️ 不一致」，请用户裁决。
- 测试通过 ≠ 行为正确：不要在技能里写「该逻辑已被测试覆盖，可安全修改」。写清覆盖了哪些用例、哪些路径没覆盖。

## 5. 时效与版本

- 在 `verification.md` 或总览里记录事实包生成时间与 git HEAD（如果扫描器给出），例如「事实基线：2026-11-01，HEAD `abc1234`」。
- 代码大改后：重新跑扫描 + 校验，再更新 `file-map.md`/`verification.md`；`architecture.md` 的语义部分需要人再确认。

## 6. 敏感信息

- 不写密钥、token、账号、内网地址、真实用户数据；只写配置项名称与获取方式。
- 日志/堆栈粘贴前脱敏（路径、域名、ID）。
- 用户口述里出现的客户名/内部代号，若与任务无关就省略。

## 7. 交付前抽查

随机挑 3 条陈述，回到代码验证；任一条对不上，全量复核再交付。
